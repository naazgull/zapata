zpt::stream_state — state transition diagram

Every place a stream's __state actually changes. Solid = a real __state assignment, dashed green = a listener event (no state is stored), dashed rose = a downstream effect, dashed violet = an API-client function call. Hover a state for where it is entered & left; hover an edge for the trigger and source. END in the enum is only a sizing sentinel for the listener-callback array (streams.h:556) — not a state. Examples are excluded.

Reachability. CONNECTED is never stored in __state; it only fires as a listener event from listen_on().

Erroring out. receive() stores ERRORING_OUT when a message can't be parsed (syntax error). send() may still finish a reply on such a stream (back to IDLE), but unmute() treats ERRORING_OUT as teardown and frees the stream's slot via erase().

Graceful close. GRACEFULLY_CLOSE is a stored state entered only by an API-client function call — stream->state(zpt::stream_state::GRACEFULLY_CLOSE), the same way the client invokes any function. The polling core supplies the teardown hook: the next unmute() of such a stream frees its slot via erase() instead of re-adding it to epoll (streams.cpp:203–205). As written today the SYNCHRONOUS guards (transport.cpp:38–41, 70–74) do not list GRACEFULLY_CLOSE, so a receive()/send() initiated while the stream is in this state trips the expect.

Synchronous cycle. The IDLE ⇄ WAITING / IDLE ⇄ PROCESSING loop runs only for transports with the SYNCHRONOUS capability; async transports leave __state untouched.

Persistent transports. amqp_stream::close() and mqtt_stream::close() reset the state back to IDLE (the self-loop on IDLE) instead of DISCONNECTED like the base class.

Source of truth: io/stream/src/streams.cpp (basic_stream + zpt::polling), network/transport/src/transport.cpp (receive()/send(), ERRORING_OUT on syntax error), network/{amqp,mqtt} (close() overrides), and io/stream/include/zapata/streams/streams.h (the enum).
